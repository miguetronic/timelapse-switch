# Test report: road C, the plugin's own copy off OBS's graphics thread

*Date: 2026-10-17. Decision: ADR-012 (experimental). Requirement: REQ-018. Run with the maintainer's approval.*

## Summary

- **Same picture.** In the verification mode (`TIMELAPSE_SWITCH_ROAD=verify`), road C and road B handed over the same frames, at the same times, byte for byte: 3009 frames compared, 0 different, 0 on one road only (1080p, scenario `standard`, 28 sections).
- **Same recording.** The integration scenarios `standard`, `pause`, `pauses` and `real` pass on road C: length, rhythm, sync, silence, chapters, pauses, totals, no lost frames, no leaks. (One `pause` run went 0.7 ms over the sync check's 30 ms limit; road B does the same in that scenario, see "Found on the way".)
- **OBS's graphics thread, 4K30.** Per frame, before the preview: 0.80 ms median on road C against 3.31 ms on road B and 0.66 ms for OBS's own recording; 1.57 ms for the worst 1 % against 5.29 ms and 1.15 ms. Road C's own step: 0.22 ms median, 0.35 ms for the worst 1 %.
- **Lighter in other ways too.** Against road B: 0.37 CPU cores instead of 0.46; 71 MB less RAM while recording, and all of it given back when the file is saved (OBS's own memory feed is never filled). The cost: 47 MB more card memory kept in RAM (GTT), the four staging slots.

## Reading it

- **OBS's graphics thread** (the "obs_graphics_thread" and "output_frame" rows): road B adds the wait for the frame (`download_frame`) and OBS's copy into its memory feed (`output_video_data`, 2.53 ms median in 4K). Road C replaces both with its own step (0.22 ms), which only asks the card for the conversion and the copy, and maps the previous frame. That is what OBS does before it renders the preview, so the preview keeps its pace.
- **"OBS frame render time"** (OBS's own statistic, mean): 3.49 ms on road B, 0.88 ms on road C, 0.70 ms for OBS's own recording.
- **The video encoder** was 66 %, 70 % and 75 % busy for OBS, road B and road C. On 2026-10-16 road B measured 76 %; the spread between runs is as large as the difference, so it is not read as a cost of road C.
- **RAM once the file is saved** is back to the idle level on road C (463 MB), while on road B OBS keeps its memory feed (534 MB) until it closes.

## Found on the way

- `tools/check.sh` listed files with `git ls-files`, so new files were checked only after their first commit; two clang-tidy findings reached a commit that way. Fixed: new files are checked too.
- The `pause` scenario's sync check can fail by a few tenths of a millisecond on road B as well (five road B runs gave -9.3, +24.0, -30.7, +24.0 and +2.7 ms for the section after the second pause). The values are steps of one frame (33.3 ms) and one audio block (21.3 ms), the rounding REQ-005 allows (half of each, 27.4 ms), shifted by about -3.3 ms. To be investigated on its own.

## Real sessions

Three sessions on the reference PC with the maintainer's own setup (a phone camera in 4K30 through LensLink, HEVC on VAAPI, a virtual machine working), recording with the plugin while watching OBS's preview. From the plugin's summary lines and OBS's profiler at exit:

| Version of road C | Plugin steps over 2 ms | Longest step | Camera pictures repeated | Preview, as seen |
|---|---|---|---|---|
| first: copy asked for after the scene, slot mapped one frame later | not counted yet (99 % under 0.4 ms) | 8.9 ms | 4 in 714 | better than road B, not as smooth as OBS's Record button |
| second: copy asked for after the preview | 343, 20 % | 12.8 ms | 51 in 841 | worse |
| final: copy asked for after the scene, slot mapped two frames later | 0 | 0.94 ms | 1 in 943 | still less smooth than OBS's Record button, and only while the plugin records |

Before road C, road B sessions repeated 1 to 5 camera pictures per few hundred moving frames, and OBS's own recording 1 in 700. The second version's order is recorded in ADR-012 so it is not tried again: the sandbox OBS of the integration test shows no preview, so only a real session could show it.

With the final version, OBS's graphics thread and the camera behave as with OBS's Record button, yet the preview still looks less smooth while the plugin records, and the rest of the desktop does not. What remains is the card's extra work of the round trip (3D engine 18 % busy against 4 %, from the cost run above), common to roads B and C. Accepted and documented: `docs/performance.md`, section 9.
